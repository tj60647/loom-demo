# Loom: Frameworks — the sign-in outage of 1–2 September 2026

**Students could not sign in for about ten hours while every page answered
`200`.** The cause was a database password that changed on one side and not the
other. No data was lost, no code was wrong, and nothing in the application had
been deployed for four days when it broke.

This is the record. It exists because the failure was invisible to every
automated check the project had, and the reasons for that are worth keeping.

## What broke

**Loom: Frameworks** runs on **Vercel**; students' work is stored in a Postgres
database at **Neon**. Every time the app reads or writes anything it has to log in to that
database, and the password it uses is kept as a setting on the Vercel project,
called `DATABASE_URL` — a copy, entered by hand.

At **16:37:52 UTC on 1 September**, Neon changed that password. The copy held in
Vercel was not updated, so from that instant the app was logging in with a
password the database no longer accepted.

From that moment nothing could authenticate. Next.js renders its pages without
data, so the site kept serving; only the data-backed paths failed. NextAuth
cannot do anything without the database — it must look up the GitHub account,
find or create the user, then write a session row — so sign-in was the loudest
casualty:

```
[next-auth][error][adapter_error_getUserByAccount]  → OAUTH_CALLBACK_HANDLER_ERROR
[next-auth][error][adapter_error_getSessionAndUser] → SESSION_ERROR
read.failed  read: getSources                        GET /api/sources → 500
```

**It was not session expiry**, which is the natural first guess. An expired
session returns zero rows, not an error, and sends the user to sign in again —
which would have worked. Here the sign-in itself threw, and `getSources`, which
never touches authentication, failed identically.

## What caused the rotation

**Loom's database does not sit on its own.** It is one of several in a shared
account, all reached with the same password. On 1 September another project in
that account was connected to the database server — an ordinary setup step, of
the kind done routinely and documented as such. The connection rotated the
shared password and delivered the new one only to the project being connected.
Loom holds its copy by hand, so nothing updated it.

**That is why this is a structural problem and not a mistake.** Nothing unusual
was done. Any comparable routine action on that account would have had the same
effect, and will, for as long as Loom's database lives alongside unrelated work
and shares a password with it.

Four timestamps, three seconds apart, make the chain unambiguous:

| Time (UTC) | Event | Where recorded |
| --- | --- | --- |
| 16:37:52.000 | `neondb_owner` `updated_at` | Neon role metadata |
| 16:37:52–54 | `apply_config` + `epc_sync` across three endpoints | Neon operation log |
| 16:37:55.452 | 16 Neon env vars created on the other Vercel project | Vercel project env |
| 16:37:55.637 | `secretRotationCompletedAt` | Vercel store record |

The last one matters: **Vercel names the event itself.** The rotation is not an
inference drawn from timing.

The store is `externalResourceId: raspy-wave-74437268` — the same Neon project
that holds `loom-db`. It was healthy throughout (`status: available`); only our
copy of the password went stale. That Neon project hosts **eight** databases
behind one role, of which `loom-db` is one, so connecting an unrelated app to it
was an ordinary act with a non-obvious blast radius.

## Why nothing noticed

Four independent reasons, and every one of them needs to be false for the next
outage to be caught quickly.

**The homepage answered `200` throughout.** Any uptime check pointed at `/` saw
a healthy site.

**The failure surfaced on a page almost nobody was watching.** Measured 5xx
across the incident window: `/reading/[sourceId]` **29**, `/api/sources` **7** —
and all seven of those were a person running `curl` during the diagnosis. That
page sees 1–45 requests an hour, well under any anomaly detector's noise floor.
Vercel's own error-anomaly detector recorded **nothing**, across the incident
and the 90 days around it.

**Overall error rate was 0.234%** (37 5xx / 15,794 requests). A "rate above 1%"
alert would not have fired. Alert on absolute counts here, not ratios.

**`DATABASE_URL` is typed Sensitive, so nobody could compare it.** A pull
returns the literal string `"encrypted"` — to the account owner as much as to
anyone. The one value everybody needed to look at was invisible to everybody.

### The rotation was per-branch, which is why CI stayed green

This is the part that most deserves keeping. Roles in Neon are per branch, each
with its own password, and the sweep took three of the five:

| Branch | `neondb_owner` last changed |
| --- | --- |
| `main` | 2026-09-01 16:37:52 |
| `staging` | 2026-09-01 16:37:53 |
| `dev` | 2026-09-01 16:37:54 |
| `ci-suite` | **2026-04-30** |
| `preview` | **2026-04-30** |

So `CI_DATABASE_URL`, set on 2 August and never touched, still worked. CI passed.
Previews deployed. **Every automated view of the system was pointed at a branch
that still worked**, while production could not authenticate at all.

`ci-suite` was in Neon's cold storage from 30 August to 2 September, which fits.
`preview` was never archived and was skipped anyway — so archiving is not the
rule, and **what selects the rotated branches is unknown.** Do not predict the
blast radius of a store connect or disconnect.

`dev` was rotated in the same sweep, so a local `.env.local` written before
16:37 on 1 September holds a password that no longer works. That follows from
the rotation; whose machines were affected was not surveyed.

### The credential was never Loom's alone

Loom is one of several applications on that database server, and they all
authenticate as the same role. The rotation invalidated every hand-set copy of
it simultaneously — Loom's among them, and not only Loom's.

That is the argument for the recommendation below, and it is worth separating
from this particular incident: **the shared database project is the hazard, not
the action that triggered it.** One ordinary configuration change, on an
application unrelated to Loom, was enough to take Loom's students offline for
ten hours. Any comparable change will do the same thing again for as long as
Loom's database shares a credential with applications Loom has nothing to do
with.

The other applications are outside this project's scope and are not tracked
here.

## What was ruled out, and how

Each was checked rather than assumed, and each was wrong:

- **Schema drift** — 30 of 30 migrations applied. It was the leading theory,
  because this exact class of failure had happened before (migration 0028,
  `section.leadUserId`, see `scripts/check-prod-migrations.ts`).
- **Neon compute suspended or over quota** — every branch reported `ready`.
- **GitHub OAuth misconfiguration** — the authorize redirect built correctly,
  right client ID and callback.
- **DNS, TLS, or a domain lapse** — `loom.aroughidea.com` resolved and served
  throughout.
- **A GitHub or CI change** — every workflow run green; last deploy four days
  earlier.

The decisive experiment was to fetch a fresh credential from Neon and run the
exact failing queries. They all succeeded, against the same host, at the moment
the application could not. That splits the world cleanly: the database is fine,
the application's stored credential is not.

## The fix

```bash
CS=$(neonctl connection-string main --project-id raspy-wave-74437268 \
       --database-name loom-db --pooled --role-name neondb_owner)
vercel env rm DATABASE_URL production --yes
printf '%s' "$CS" | vercel env add DATABASE_URL production --sensitive
vercel redeploy <production-deployment-url>
```

Verified against the database: `sessions` 412 → 413 and
`users` 63 → 64 as people signed back in. **The new user is the strongest
evidence** — creating one exercises the whole path that was broken
(`getUserByAccount` → `createUser` → `createAccount` → `createSession`), not
just a read recovering.

## What changed as a result

- **`/api/health`** — `select 1`, 200 or 503, no session, no payload. It exists
  to be asked on a schedule by something outside the deployment, turning a rare
  invisible data failure into a frequent deterministic 5xx.
- **`.github/workflows/heartbeat.yml`** — asks it every fifteen minutes, and a
  README badge puts the answer where someone will see it. Two honest limits are
  stated in the file: GitHub delays scheduled runs and disables them after 60
  days of repository inactivity.
- **`PROD_DATABASE_URL`** — configured, so `check:prodmigrations` stops skipping
  green. It uses `ci_migration_reader`, a role that can read
  `drizzle.__drizzle_migrations` and nothing else — verified unable to read
  `public.user`, `session`, `course`, `passage`, or create tables. It ran for
  the first time on 2 September and reported 30/30.
- **A Vercel alert rule** scoped to this project on 5xx. Treat it as a
  supplement: the same detector was live during the outage and recorded
  nothing, and custom metric alerts are capped at 0 on this plan.
- **The Neon `ci` branch is now `ci-suite`**, because three things wore the
  letters CI and the collision cost real time here.
- **Four stale preview `DATABASE_URL` entries were deleted** — leftovers from
  closed PRs that `teardown` had not removed, each holding a Neon credential.
  The branch-scoped entry for the one still-open PR was kept.
- **One `.env.local` was repaired** — the one on the machine this
  investigation ran from. Others were not surveyed.

## Still open

- **Nothing prevents a recurrence.** This project is not connected to the Neon
  store holding its own database, so a hand-set `DATABASE_URL` cannot receive a
  rotation. Connecting it is not a simple fix: the integration injects one
  value across production, preview and development with no branch scope, which
  would point unscoped previews at `main` — and previews are keyless, since
  `PREVIEW_LOGIN_SECRET` is never set. Giving the app its own Neon role, whose
  password the integration does not manage, is the likelier answer.
- **What selects the rotated branches** is unknown (see above).
- **Detection still depends on the heartbeat**, which is the weakest of the
  available monitors. An external uptime check needs no Vercel or Neon access
  and has neither of GitHub's limits — but it needs an owner, and an alert
  nobody owns is worse than none.
- **Other projects in that account hold credentials that reach this database.**
  The shared role reaches every database in the Neon project, `loom-db` among
  them. Nothing suggests it is used that way, and the other projects belong to
  the same person — but it is a standing path to student work from unrelated
  software, and it ends when the database moves rather than needing separate
  attention. Untangling it beforehand would rotate the password again and take
  students offline a second time.
- **Nobody owns any of this yet.** Responsibility for the production
  deployment spans four systems that do not share an owner by default — the
  Vercel project and its Sensitive variables, the shared Neon project, the
  GitHub repository and its Actions secrets, and the monitoring, including who
  receives an alert and is expected to act on it. Every item above needs a
  name against it. In this incident the person looking had the right
  hypothesis and no route to act on it, and the person who could act did not
  yet know there was anything to act on; that is an ownership failure rather
  than a technical one, and it is the one thing here that no code fixes.

## The one-line version

*The site was up; sign-in was down; the difference was a password nobody could
read, on a branch nobody was watching.*
