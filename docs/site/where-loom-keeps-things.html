Loom · how the back end is put together

Where Loom Keeps Things

Loom stores two very different kinds of thing, in two very different places. Once you can tell those apart, everything else about the setup follows from it.

Two kinds of storage

People often say "the database" to mean everything Loom saves. It's worth splitting in two, because the two halves follow opposite rules.

The database

Everything people write and do.

Accounts and course rosters. Which readings belong to which course. Every passage a student marks, every projection they build, every note and link between them.

Thousands of small pieces of text, changing every minute someone is working.

File storage

The readings themselves.

The PDF files students open, plus the pictures Loom generates from them — the cover on each card in the Library, and the page images behind the reading view.

A reading's file is never edited in place. Improving one adds a new version alongside the old, so this store only ever grows.

The rule worth remembering: each copy of Loom has its own database, but they all share one set of reading files.

Five copies of Loom

The same app runs in five places at once. They differ only in who is looking at them and how finished the work is — from a single developer's machine through to the site students use.

The databases, and one shelf of files

A developer's laptop works against the same database as the tester site, so anything you make while building shows up there too. Work-in-progress previews are different: each piece of proposed work gets a database of its own, made fresh and thrown away when the work is finished or abandoned.

One shelf of reading files Shared by every copy of Loom — files are added, never replaced
Student database The student site Real student work. Nothing else can reach it.
Tester database The tester site · developers' laptops Its own drawer for pictures it makes
A database per proposal Each work-in-progress preview Made from a clean copy, deleted when the work closes
Checks database The automated checks Its own drawer for pictures it makes

Each began as a copy of another, taken once. From that moment on they go their own way — and the per-proposal ones are copies made new every time, so nothing anyone tries there can reach the others.

Storing five copies of every PDF would waste space and let them drift apart, so there is one set and everybody reads from it. But anything a copy of Loom makes — a cover image, a page picture — goes into a drawer labelled with that copy's name.

That is what keeps the copies from treading on each other. The student site's covers can't be overwritten by someone's half-finished work, and only the student site can remove a reading's file for good.

Readings have versions

Many of our readings are scans, and a scan's words often come through garbled — which means students can't select, search or highlight them properly. Fixing that produces a corrected file. The old one isn't thrown away or written over: the new version is added beside it.

Version 1 The file as first uploaded The student site still points here
Version 2 Same reading, words corrected The tester site points here

Both files sit on the shared shelf, permanently. What differs between copies of Loom is which one each is pointing at — and that pointer lives in the database, which is why it can differ from one copy to the next.

So a correction doesn't reach students the moment the work is finished, or even when the code is next updated. The corrected words are content, not code. Someone has to point the student site at the new version deliberately — and Loom keeps a record of every such move: which file, which one it replaced, and why.

What travels between copies

This is the part most easily misunderstood, so it's worth being exact: the shape of a database travels, and its contents never do.

Travels

The shape

Say we decide readings should carry a due date. Someone writes that down as an instruction — "add a due date to readings" — and that instruction file travels along with the code.

It's run against each database in turn: testers first, students last. All four end up built the same way.

Never travels

The contents

Student work stays on the student site. Tester work stays on the tester site. Nothing copies one database's contents into another, in either direction.

There's no button for it and there shouldn't be — the copies are meant to diverge. They match in construction, not in what's inside.

Corrected readings count as contents, not code, which is why they have to be pointed at deliberately on each copy.

So "updating the student site" changes how its database is built. It never replaces what's in it.

Words you'll hear

The technical names for the same things, in case they come up in a meeting or a message.

environmentOne of the five copies of Loom.
