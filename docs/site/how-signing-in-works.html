Loom · who gets in, and where

How Signing In Works

Loom has no passwords of its own. Everyone signs in through GitHub, and the course roster — not GitHub — decides who is actually let in.

Two doors

There are only two ways into Loom, and they both ask the roster the same question at the same moment.

The main door

Sign in with GitHub

You click one button and GitHub confirms who you are. Loom never sees your password and never asks for one.

It asks GitHub for one thing only: your confirmed email addresses. If GitHub's consent screen ever asks for more than that, something has gone wrong and it's worth saying so.

Working on the tester site and the student site
The side door

A link in your inbox

For someone invited to a course who has no GitHub account and won't be getting one. Loom emails a single-use link, good for 24 hours, that signs them in when clicked.

It's folded away on the sign-in page rather than offered up front — for almost everyone, GitHub is the right answer and a visible choice is just one more decision.

Built, but not switched on anywhere yet — the sign-in page currently links to it without it being there

The roster decides, and decides first

Having a GitHub account does not get you into Loom. When someone arrives at either door, Loom takes the email address and checks it against the course rosters. If no course has invited that address, they don't get in — they get a page telling them so, naming the address they arrived with, so they can see whether it's the one you invited.

This runs before anything else happens. For the emailed door that means an uninvited address never even receives a link. There is no way to be "signed up but not on a course": in Loom those are the same thing.

So adding someone to Loom is always the same act — invite their email address to a course. They're enrolled automatically the first time they sign in.

One useful detail: people often have several email addresses on their GitHub account. Loom looks at all the confirmed ones and prefers whichever the roster already knows — so a student whose personal address is their main one still gets matched on their university address.

Which door works where

Sign-in doesn't work the same way on all five copies of Loom. This is the part that trips people up, and it's the reason previews are for looking rather than doing.

Why a preview can't offer GitHub sign-in

When you sign in with GitHub, GitHub has to send you back to where you came from. For safety it will only send you to one fixed web address, registered in advance — so that nobody can point a copycat site at your account.

Every work-in-progress preview has its own web address. None of them is the registered one, so GitHub refuses to send anyone back. That's a safety rule working exactly as intended, not a bug and not an oversight — but it does mean the team can't sign in to review each other's work.

A team door — what we did

The developers' test door, opened on previews only. It needed the preview database sealed off from real data first, which is why previews now carry the readings and the test accounts and nobody's work.

Use the emailed link

The side door needs no registered address at all — the link simply points back wherever it came from. Switching it on would work on every preview immediately.

Fixed addresses for review

Give a small number of review sites permanent addresses and register each with GitHub. Real sign-in, but one setup per site and it doesn't scale to many.

What signing in gets you

Loom doesn't ask anyone to pick a role. What you can do follows from how you were invited.

A learner

Invited to a course. Sees that course's readings, and everything they mark and build is their own.

Faculty

Invited into a course's faculty group. Can see the cohort's work as a whole, without being able to edit it.

An admin

Runs the library and the rosters: uploading readings, inviting people, building courses.

Enrolment is automatic and happens the first time someone signs in — Loom looks at every course that invited their address and puts them in all of them. Removing someone from a course removes what that gave them; it doesn't delete the work they did.

Words you'll hear

callback URLThe one fixed address GitHub is willing to send people back to. The reason previews can't offer GitHub sign-in.
rosterThe list of email addresses invited to a course. The thing that actually decides who gets in.
invitationAdding an email address to a course's roster, before that person has ever signed in.
enrolmentWhat happens automatically on someone's first sign-in: they're placed in every course that invited them.
sessionThe record that you're signed in. Kept by Loom, not by your browser alone, so signing out really does end it.
