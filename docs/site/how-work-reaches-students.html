Loom · how a change travels

How Work Reaches Students

Every change to Loom takes the same path through five stops. Each one answers a question none of the others can, and nothing skips ahead — including work that's finished and obviously right.

The five stops

The same change moves along this path, gathering confidence. Early stops are fast and private; later ones are slower and more public. That order is the whole design — a mistake caught at stop two costs minutes, and the same mistake found at stop five costs a student's afternoon.

1
Someone builds it a developer's own machine

A developer works on one change at a time, running Loom privately and trying it as they go. Nobody else sees anything yet, and nothing they do here can affect anyone.

Who's watchingOnly them
The questionDoes it do what we meant?
How longHours to a few days
2
The machines check it automated checks

The change is proposed, and a machine rebuilds Loom from scratch and replays a scripted run through it — signing in, opening a reading, marking a passage, building a projection — to see whether anything that used to work has stopped.

Who's watchingNobody; it reports back
The questionDid this break something that worked?
How longMinutes, automatically
3
The team looks at it a preview

The unfinished change gets its own web address, so anyone on the team can open it and form an opinion without installing anything. This is where "is this the right thing?" gets settled, while it's still cheap to change the answer.

Who's watchingThe team
The questionIs this right, and does it look right?
How longAs long as the discussion takes
4
Testers use it the tester site

Once a change is agreed and reviewed, it joins everything else on the tester site, where alpha testers do real work with it. It sits here a while on purpose. Changes that seemed fine on their own often disagree with each other, and only use finds that.

Who's watchingAlpha testers
The questionDoes it hold up alongside everything else?
How longDays — deliberately
5
Students get it the student site

Promotion to students is a separate, deliberate act — never automatic, and never done from somebody's laptop. It asks a different question than the review did: not "is this built well?" but "is this what students should meet?"

Who's watchingStudents
The questionIs this what students should meet?
How longLive from the moment it lands

What has to be true to move on

Only two of the four moves are gated, and they're gated differently — because they're protecting different people.

Anyone can make a preview No gate at all. Pushing work up creates its preview automatically — that's what makes stop 3 cheap enough to actually use.
To reach testers The automated checks pass, and another developer has read the change and agreed with it. Two conditions, both mechanical to confirm.
To reach students The checks pass again, and an owner approves. This one is a judgement, not a formality — it's the last point at which "correct" and "right for students" can still come apart.

Two things that don't ride along

The path above carries the app — what Loom can do. Two important things travel differently, and expecting them to arrive with a change is the most common way to be surprised.

Corrected readings

Fixing a scan's garbled words produces a corrected file, and that's content rather than code. It doesn't ride along when a change is promoted — each copy of Loom has to be pointed at the corrected version deliberately.

So the tester site can be showing readable, searchable text while students are still on the garbled original. Worth checking before a course starts, not after.

Signing in with GitHub

Real sign-in works on the tester site and the student site. It can't work on a preview: sign-in has to be registered against one fixed web address in advance, and every preview has its own.

That's a technical constraint rather than a decision, but it shapes the work — which is why stop 3 is mostly about looking, and stop 4 is where anything involving accounts gets tested.

Right now, a preview offers no way to sign in at all, so treat stop 3 as look-don't-touch. Work needing an account is done privately at stop 1 or on the tester site at stop 4. This is being worked on, and this paragraph goes away when it is.

The rhythm

One change per branch, days not weeks. A small change reviewed the same day beats a large one that waits — and a branch that lives for a month turns review into "approve my month".

Branches map to changes, never to people. There's no release schedule and no ceremony: work moves when it's ready and someone has looked at it, which for a small change can be the same afternoon.

Words you'll hear

The names people will actually use for the stops and the moves between them.

branchOne change being worked on, kept separate from everyone else's until it's ready.
pushSending work up from a laptop so others can see it. This is what creates a preview.
pull request · PRThe formal proposal to fold a change in, and the place the discussion about it happens.
reviewAnother developer reading the change and saying yes, or asking for something.
mergeFolding an approved change in with everything else. This is what moves it to the next stop.
CI · checksThe automated re-testing at stop 2. "CI is green" means everything passed.
soakDeliberately leaving a change on the tester site a while, so real use can find what review couldn't.
deployPutting a version of the app onto one of the sites.
rollbackPutting the previous version back, if something reaches students and shouldn't have.
